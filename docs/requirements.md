# Tauri アプリケーションテンプレート 要件定義

このドキュメントは、Tauri v2 でアプリ開発を始めるためのテンプレートリポジトリに
「何を含めるか」を洗い出したものです。実装の設計図ではなく、スコープの合意を取るための一覧です。

---

## 1. 目的とスコープ

### 目的

新規 Tauri アプリを立ち上げるとき、毎回発生する以下の作業をゼロにする。

- ビルド基盤・型共有・Lint・CI の初期構築
- デスクトップ／モバイル両対応のためのプラットフォーム分岐の設計
- ロギング・設定永続化・DB・エラーハンドリングといった「どのアプリでも要る」土台
- 署名とリリース配信のパイプライン

### スコープに含むもの

- 動作するサンプル実装を伴う、そのまま開発を開始できる状態のテンプレート
- Windows / macOS / Linux / iOS / Android の 5 ターゲット
- CI（検証）と CD（リリース）のワークフロー
- テスト駆動開発を回せるテスト基盤と、その進め方の規約
- レビュー観点の明文化と、Copilot によるレビューの設定
- 開発者向けドキュメントと規約

### スコープに含まないもの

- 特定ドメインの業務ロジック
- 認証基盤やバックエンドサーバーの実装（連携するための足回りのみ用意する）
- ストアへの申請作業そのもの（成果物の生成までを担当）

| Lint / Format (Rust) | rustfmt + clippy | |
| 対応 OS | Windows / macOS / Linux / iOS / Android | |

## 3. プラットフォーム別の対応可否

モバイルを含めるため、テンプレートは **共通コア + デスクトップ拡張 + モバイル拡張** の三層構造とする。
Rust 側は `#[cfg(desktop)]` / `#[cfg(mobile)]`、TS 側は実行時のプラットフォーム判定で分岐する。

| 機能 | Desktop | Mobile | 備考 |
|---|:--:|:--:|---|
| システムトレイ / ネイティブメニュー | ○ | — | デスクトップ専用 |
| グローバルショートカット | ○ | — | |
| ウィンドウ状態の復元 | ○ | — | |
| 自動起動 | ○ | — | |
| 単一インスタンス制御 | ○ | — | |
| 自動アップデート (updater) | ○ | — | モバイルはストア配信のため使用不可 |
| ディープリンク | ○ | ○ | 登録方法が OS ごとに異なる |
| 通知 / ダイアログ / FS / HTTP / SQL | ○ | ○ | 権限要求のフローがモバイルでは別途必要 |
| 生体認証 | — | ○ | モバイル専用 |

UI も、トレイ常駐前提のデスクトップ画面とタッチ前提のモバイル画面は別物になるため、
**レスポンシブ設計とセーフエリア対応を初期段階から組み込む**。

### 4.5 品質・テスト（TDD 前提）

本テンプレートは **テスト駆動開発（TDD）を前提とした開発サイクル** を標準とする。
そのためテスト基盤は「後から足すもの」ではなく P0 の土台として扱い、Phase 1 の時点で
Red-Green-Refactor が両言語で回る状態にする。進め方の詳細は §9 に定義する。

| ID | 要件 | 優先度 |
|---|---|:--:|
| QA-01 | Biome による lint / format（CI で違反を失敗扱い） | P0 |
| QA-02 | rustfmt + clippy（`-D warnings`） | P0 |
| QA-03 | TypeScript の型チェックを CI に組み込む | P0 |
| QA-04 | フロントのテスト基盤（Vitest + Testing Library）と、失敗するテストから書き始めるサンプル | P0 |
| QA-05 | Tauri IPC のモック層 — Rust を起動せずにコマンド呼び出しをテストできる状態（`@tauri-apps/api/mocks`） | P0 |
| QA-06 | Rust のテスト基盤 — モックアプリ経由でコマンドの入出力を検証できる雛形（`tauri::test`） | P0 |
| QA-07 | DB を含むテストの雛形（インメモリ SQLite を用い、テストごとに独立したスキーマを構築する） | P0 |
| QA-08 | ウォッチモードの整備（TS / Rust 双方）— TDD の回転速度を担保する | P0 |

### 4.9 レビュー体制

レビュー観点を明文化し、それを **Copilot・人間・AI エージェントの 3 者が同じ基準として参照する** 構造にする。
観点そのものは §10 に定義し、各ツールの設定ファイルはそこから導出する。
観点を書く作業がそのままレビュー基準の定義になるため、これは実装より前に着手する。

| ID | 要件 | 優先度 |
|---|---|:--:|
| REV-01 | レビュー観点チェックリストを `docs/review-checklist.md` として単一の正本にする（§10 が原案） | P0 |
| REV-02 | `.github/copilot-instructions.md` — リポジトリ全体に効く Copilot 向け指示。技術スタック・禁止事項・レビュー観点を記述する | P0 |
| REV-03 | パス別のレビュー指示（`src-tauri/**`、`src/**`、`.github/workflows/**` で見るべき点が異なるため分割する） | P1 |
| REV-04 | PR に対する Copilot コードレビューの自動リクエスト（リポジトリのルールセットで設定） | P1 |
| REV-05 | 自動生成ファイルをレビュー・差分検出の対象から除外する設定（`bindings.ts`、lockfile、`components/ui/` 等） | P1 |
| REV-06 | PR テンプレートに、観点に対応した自己チェック項目を埋め込む | P1 |
| REV-07 | `CLAUDE.md` に同じ観点を反映し、AI エージェントが実装時点で自己チェックできるようにする | P1 |
| REV-08 | レビュー観点の更新フローの明文化（不具合を出したらその観点を追加する、という運用） | P2 |

## 6. 想定されるリスク・注意点

| # | 内容 | 対応方針 |
|---|---|---|
| R-1 | sqlx のコンパイル時 SQL 検証は、ビルド時に DB かオフラインデータを要求する | オフライン用のクエリメタデータをリポジトリにコミットし、CI で最新性を検証する |
| R-2 | SQLite のネイティブライブラリを iOS / Android 向けにクロスコンパイルする際に詰まりやすい | 早期にモバイルビルドを通して構成を確定させる。難航する場合はモバイル側の DB 利用を段階導入とする |
| R-3 | 署名・公証には有償のアカウントと証明書が必要 | 証明書が無くても CI が通るよう、署名ステップは秘密情報の有無で分岐させる |
| R-4 | iOS のビルドは実行環境と証明書管理の要求が重い | 初版では P2 とし、Android を先行させる |
| R-5 | tauri-specta の生成物とソースがずれると実行時に壊れる | CI で再生成し差分が出たら失敗させる |
| R-6 | デスクトップ専用機能が増えるほどモバイルビルドが壊れやすい | CI にモバイルのコンパイル確認を早期から入れる |
| R-7 | フル装備ゆえに不要機能の削除コストが発生する | 機能ごとにファイルを分離し、削除手順を docs に記載する |
| R-8 | Copilot は指示ファイルに書かれた観点しか見ず、大きな差分では取りこぼす | 一次フィルタと位置づけ、人間のレビューを代替させない。PR を小さく保つ運用と対で扱う |
| R-9 | 自動生成ファイルを除外しないと、Copilot のレビューがノイズで埋まる | REV-05 を早期に入れる |
| R-10 | Tauri のコマンドは実アプリを起動しないとテストしづらく、TDD が回らない | ロジックをコマンドから分離する設計制約（§9.3）を規約として強制する |
| R-11 | Rust のビルドが重く、TDD の 1 サイクルが長くなる | ロジックを別クレートに切り出すなど、テスト対象を小さく保つ構成を検討する |

## 7. 未決事項（次に決めるもの）

1. **ルーティングと状態管理の具体的なライブラリ** — ルーター、クライアント状態、非同期状態のそれぞれ
2. **i18n の要否と対象ロケール** — 初版で日英 2 言語を入れるか、仕組みだけ用意するか
3. **外部 API 連携の具体像** — OAuth を行うか。行う場合、ディープリンクでのコールバック受けが必須になる
4. **アップデータの配信先** — GitHub Releases か、自前のストレージか

6. **クラッシュレポートの外部送信** — 収集サービスを入れるか、ローカルログのみに留めるか

## 9. TDD の進め方

### 9.1 基本サイクル

1. **Red** — 失敗するテストを先に書く。仕様を「振る舞い」として表現する
2. **Green** — テストを通す最小限の実装を書く
3. **Refactor** — テストが緑のまま構造を整える

このサイクルを回せることが Phase 1 の完了条件であり、テスト基盤は最初から用意する。

### 9.2 層ごとの適用方針

TDD が有効に働く層とそうでない層を分ける。全てに機械的には適用しない。

| 層 | 適用 | テスト手段 |
|---|:--:|---|
| Rust: ドメインロジック・純粋関数 | 必須 | ユニットテスト |
| Rust: DB アクセス | 必須 | インメモリ SQLite に対する統合テスト |
| Rust: コマンド層 | 推奨 | モックアプリ経由で入出力を検証 |
| Rust: OS 連携（トレイ・通知・FS） | 対象外 | 薄いラッパーに留め、手動確認とする |
| フロント: hooks・ストア・変換ロジック | 必須 | Vitest |
| フロント: コンポーネント | 推奨 | Testing Library（振る舞い単位。スナップショットは使わない） |
| フロント: 画面全体の結線 | 対象外 | E2E で担保する |

### 9.3 テスト可能性を担保する設計制約

TDD を回すには実装側の構造が前提になる。以下をテンプレートの設計規約として強制する。

- **コマンドを薄く保つ** — `#[tauri::command]` は入力の変換・検証とロジック関数の呼び出しだけを行う。ロジックはアプリハンドルに依存しない純粋な関数・構造体として切り出し、それ単体でテストする
- **副作用を境界に寄せる** — ファイル I/O・HTTP・時刻取得はトレイト越しに扱い、テストでは差し替える
- **DB 接続は引数で受け取る** — グローバル状態から取得しない。テストごとに独立した接続を渡せるようにする
- **フロントは生成された bindings を直接呼ばない** — 一段ラップし、テストではその層を差し替える。IPC そのもののモックが必要な場合のみ Tauri のモック機構を使う

### 9.4 回転速度の担保

1 サイクルの待ち時間が長いと TDD は破綻するため、以下を初期整備の対象とする。

- フロントのユニットテストはウォッチモードで即時に再実行される
- Rust のテストは変更検知で自動再実行される。ビルドが重いため、テスト対象を小さく保つクレート構成も検討する
- **アプリの起動を伴うテストはサイクルに入れない** — E2E とネイティブ機能の確認は PR 前・CI 側に置く

### 9.5 CI との関係

- PR チェックではユニット・統合テストを全て実行する
- E2E は別ワークフローとし、TDD の速度を犠牲にしない
- テストの無い変更を機械的に弾く仕組みは入れない（誤検知が多いため）。代わりにレビュー観点（§10.5）で担保する

## 10. レビュー観点（原案）

`docs/review-checklist.md` の原案であり、Copilot 向け指示ファイルもここから導出する。
**Copilot は書かれた観点しか見ない** ため、この一覧の網羅性がレビュー品質を直接決める。

### 10.1 セキュリティ / Tauri 固有

- capabilities に権限を追加していないか。追加している場合、その window・その機能に本当に必要な範囲か
- フロントから受け取った値を、検証せずファイルパスやシェル引数に渡していないか
- 機密情報（トークン・鍵・パスワード）がフロントに返っていないか、ログに出ていないか
- CSP を緩めていないか。`withGlobalTauri` を有効化していないか
- 外部から受け取った URL・パスの検証があるか

### 10.2 Rust

- コマンド経路に `unwrap()` / `expect()` / `panic!` が無いか（プロセスごと落ちる）
- エラーが握り潰されていないか。共通エラー型に変換されてフロントに伝わるか
- ロックを保持したまま `await` していないか
- ブロッキング I/O を非同期コンテキストで直接呼んでいないか
- SQL が文字列連結で組まれていないか。コンパイル時検証を通っているか
- マイグレーションが既存データを壊さないか（追加のみか、破壊的か）
- ロジックがコマンド関数に直接書かれていないか（テスト不能になる。§9.3）

### 10.3 プラットフォーム分岐

- デスクトップ専用 API が共通コードに混入していないか（モバイルビルドが壊れる）
- `#[cfg(desktop)]` / `#[cfg(mobile)]` の対になる実装が揃っているか
- 追加した機能がモバイルで意味を持つか。持たない場合、UI 側でも出し分けているか

### 10.4 フロントエンド

- 生成物（`bindings.ts`）を手編集していないか
- Rust 呼び出しのエラーがハンドリングされ、ユーザーに伝わるか
- ローディング状態が表現されているか（ネイティブ処理は数秒かかりうる）
- デスクトップ幅・モバイル幅の双方で崩れないか。セーフエリアを考慮しているか
- テーマトークンを使っているか（色を直接書いていないか）
- ハードコードされた文言が i18n の対象になっていないか

### 10.5 テスト

- 変更された振る舞いに対応するテストがあるか
- テストが実装の内部構造ではなく振る舞いを検証しているか
- テスト名から「何が保証されているか」が読めるか
- テスト間に実行順依存や共有状態が無いか
- 失敗ケース・境界値が含まれているか

### 10.6 その他

- 依存を追加した理由が妥当か。バンドルサイズとライセンスを確認したか
- 設定値がハードコードされていないか
- ドキュメント（README / architecture）の更新が必要な変更ではないか

### 10.7 Copilot に任せないもの

- 自動生成ファイル（`bindings.ts`、lockfile、`components/ui/` のコピー物）は除外設定を入れ、レビュー対象から外す
- アーキテクチャの妥当性や機能の要否といった判断は、人間のレビューに残す
- Copilot のレビューは人間のレビューを代替しない。**観点の取りこぼしを減らす一次フィルタ** と位置づける
